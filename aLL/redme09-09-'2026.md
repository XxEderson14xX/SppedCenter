### 📌 Aprendizajes reales de despliegue (aplican a TODAS las Edge Functions)
- El slug de una Edge Function no se puede renombrar (si nace `hyper-processor`,
  esa es su URL). Ponerle el nombre correcto desde el inicio.

  el preflight CORS. Solución: apagarlo (la función ya valida token+rol).
- "non-2xx status" al crear usuario = revisar Logs; causa típica: perfil admin

## 📦 V6 · Identidad permanente + captura inline desde la cotización ✅ COMPLETADA

Objetivo: que todo se capture desde la cotización (sin popups ni pasos
previos) y que el historial nunca se rompa, aun cuando cambien datos volátiles
como la placa o el teléfono.

### 🧠 La regla de oro de V6
> **"La identidad NUNCA cambia; los datos de contacto SÍ."**

| Entidad | Identidad permanente (ancla del historial) | Datos que cambian (con historial/alerta) |
|---|---|---|
| 👤 Cliente | `id` interno (uuid) | Teléfono, correo, dirección, nombre |
| 🚗 Vehículo | VIN / NIV | Placa (con vigencia), color, km |

### 🔑 Decisiones de diseño
- VIN como identidad del auto: en México las placas se re-emplacan cada ~5-6
  años, pero el auto es el mismo. El VIN es permanente → el historial sobrevive.
- Placa temporal: si no hay VIN a la mano, se usa la placa temporalmente y se
  agrega el VIN después sin perder historial.
- ID interno del cliente como identidad: el teléfono también cambia; el cliente
  se ancla a su `uuid`. Teléfono/correo son datos editables con historial.
- Anti-duplicado por teléfono: al capturar un cliente nuevo, si el teléfono ya
  existe (incluso en teléfonos anteriores), se avisa y se ofrece reutilizarlo.
- Un cliente, varios autos: cada auto se liga al mismo cliente sin duplicarlo;
  cada placa/VIN conserva su propio historial.

### Piezas de V6
- `V6_01_base_datos_completo.sql` (con RLS incluido):
  - `vehiculos.vin` (único parcial) + `vehiculos.version`.
  - `placas_historial` + `cambiar_placa()` + trigger de siembra.
  - `telefonos_historial` + `cambiar_telefono()` + trigger de siembra.
  - `buscar_clientes()`, `telefono_existente()`, `buscar_vehiculo()`.
  - `resolver_cliente_vehiculo()` → alta integral cliente+auto desde la cotización.
- `index.html`, `app.js`, `styles.css` completos con la captura inline.

### 📌 Aprendizaje de seguridad
Toda tabla nueva debe nacer con RLS + políticas. Supabase avisa "tables
without RLS"; NO usar "Run and enable RLS" (bloquea sin políticas). Incluir las
políticas en el propio script.

### 🎯 Objetivos de V6
- [x] VIN como identidad permanente + historial de placas.

- [x] Anti-duplicado de cliente por teléfono/nombre/correo.

- [x] Un cliente con varios autos; cada placa/VIN con historial propio.

## 📦 V7 · Administración total de usuarios + gate de pagos ✅ COMPLETADA

Objetivo (25 Ago 2026): cerrar el módulo de usuarios permitiendo eliminar
usuarios y restablecer contraseñas desde el panel, más una mejora de UX en
las pestañas de la cotización.

### 🔐 Nuevas capacidades de usuarios
- Restablecer contraseña de cualquier usuario (el admin define la nueva).
- Eliminar usuario (borra `auth.users` + su perfil), con confirmación.

### Por qué necesitó una Edge Function
Borrar usuarios y cambiar contraseñas operan sobre `auth.users`, que solo se puede
tocar con la `service_role` key desde el servidor — nunca desde el frontend.

### Piezas de V7
- Edge Function `gestion-usuario` (`functions/gestion-usuario/index.ts`):
  - Acción `cambiar_password` → `admin.auth.admin.updateUserById`.
  - Acción `eliminar` → borra perfil + `admin.auth.admin.deleteUser`.
  - Valida sesión + rol administrador activo.
  - Candado de seguridad: un admin no puede eliminar ni cambiar su propia
    cuenta desde el panel (evita quedarse fuera del sistema).
- Ediciones frontend (por bloques):
  - `index.html` → campo "Nueva contraseña" + botón "Restablecer" + botón rojo
    "Eliminar usuario" en el modal de perfil.
  - `styles.css` → estilo `.btn.peligro` (rojo) para el botón eliminar.
  - `app.js` → limpiar campo password al abrir; listeners de restablecer y eliminar
    (con lectura del mensaje real de la función aunque sea non-2xx).

### 🧩 Mejora de UX incluida (gate de pagos)
En una cotización nueva (sin guardar), las pestañas Pagos / Seguimiento /
Archivos muestran un aviso elegante ("guarda primero la cotización") y sus
botones se ven bloqueados. Al guardar, se activan automáticamente.
(Reemplaza el `alert()` feo por un aviso integrado a la interfaz.)

### 📌 Aprendizaje de despliegue
El caché de GitHub Pages es agresivo: tras subir `app.js`/`styles.css`, hacer
Ctrl+Shift+R o abrir en incógnito. Un botón que "no hace nada" y una Console
en silencio = versión vieja de JS en caché.

### 🎯 Objetivos de V7
- [x] Restablecer contraseña desde el panel (Edge Function segura).
- [x] Eliminar usuario desde el panel (con confirmación y candado anti-autoborrado).
- [x] Gate de pestañas Pagos/Seguimiento/Archivos (aviso + botón bloqueado).
- [x] Probado en producción (funcionando tras limpiar caché).

- **Sincronización automática:** al crear la Orden de Trabajo, se copian de
  forma automática los conceptos de la cotización cuyo tipo sea
  `refaccion_libre` o `consumible` (se excluyen `servicio`, `mano_obra`,
  `descuento` y `nota`), evitando captura doble.
- Botón opcional "🔄 Sincronizar desde cotización" para volver a jalar los
  cambios si la cotización se edita después de creada la OT.
- Solo **Recepción/Administrador** pueden agregar o quitar piezas; el
  técnico las ve en modo solo lectura. Las piezas también se imprimen en el
  PDF de la orden.

### Permisos por rol (frontend)
- **Cotización:** se bloquea la edición de cliente, vehículo, kilometraje y
  fecha de entrega cuando el estado comercial es Autorizada, Cerrada,
  Cancelada o Rechazada (el **Administrador siempre puede editar**, para
  corregir errores). Adicionalmente, los roles **Consulta** y **Técnico**
  quedan en solo lectura total dentro del modal de cotización (no pueden
  crear cotizaciones nuevas, ni ver/operar la pestaña de Pagos); solo pueden
  ver datos y descargar el PDF.
- **Orden de Trabajo:** el rol **Consulta** solo puede ver e imprimir (no
  marca checklist, no cambia técnico, no guarda avance ni finaliza).
  Recepción, Administrador y Técnico sí pueden operar la orden.
- Se muestra el **técnico asignado** directamente en la cotización (tomado
  de la última orden de trabajo ligada), sin necesidad de abrir la OT.

### Historial de clientes (nuevo)
- Nuevo botón "Historial" en la tabla de Clientes que reutiliza el modal de

  del cliente y **todas sus cotizaciones** en una sola vista de principio a
  fin (KPIs de visitas, total facturado histórico y saldo pendiente
  acumulado, lista de vehículos, línea de tiempo de seguimiento).

### 📌 Aprendizaje importante de esta versión (seguridad)
Todo el bloqueo de permisos por rol descrito aquí es **frontend/UI**
únicamente: mejora la experiencia y evita errores de captura, pero **no es
seguridad real**, ya que un usuario con conocimientos técnicos podría
saltárselo llamando directo a la API de Supabase. Este hallazgo motivó
directamente la auditoría de seguridad real documentada en **V11.4**.

## 📦 V11.3 · Branding SpeedCenter + fix de menú lateral ✅ COMPLETADA

Objetivo: reemplazar la identidad genérica ("Taller Automotriz", azul/verde
de plantilla) por la marca real del negocio, cuidando la ergonomía visual
para jornadas de 8 horas frente a la pantalla; y corregir un bug de
usabilidad detectado en el menú lateral.

### Decisión de diseño (branding vs. interfaz)
Se separó el **color de marca puro** (usado en fachada, uniformes y PDFs)
del **color de interfaz** (usado en el sistema web), siguiendo la práctica
de sistemas internos de marcas automotrices: reservar el rojo/negro "puro"
para los puntos de identidad (logo, botón principal, selección activa) y

## 📦 V11.4 · Auditoría y blindaje de seguridad real en Supabase ✅ COMPLETADA

Objetivo: cerrar la brecha señalada como aprendizaje en V11.2 — los
permisos por rol aplicados hasta ese momento eran solo de frontend (UI) y
no impedían que alguien con conocimientos técnicos operara directo contra
la API de Supabase saltándose el sistema. Esta versión audita y corrige
la seguridad real a nivel de base de datos, usando el **Security Advisor**
de Supabase como guía y verificando cada corrección con consultas directas
a los catálogos del sistema (`pg_proc`, `pg_policies`,
`information_schema.routine_privileges`) antes de aplicar cualquier cambio.

### Metodología seguida (importante para futuras auditorías)
Ante los primeros intentos de corrección, se detectó que **adivinar**
nombres, parámetros o roles de los objetos de base de datos produce errores
(`function does not exist`, revocaciones que no surten efecto porque el
permiso real vivía en `PUBLIC` y no en `anon`, etc.). A partir de ese punto
se estableció como regla de trabajo: **pedir siempre los datos reales de la
base con una consulta de verificación antes de escribir cualquier `ALTER`,
`REVOKE`, `DROP POLICY` o `CREATE POLICY`.** Todo lo documentado abajo fue
confirmado así, paso a paso, con evidencia.

### Hallazgo 1 · `vista_usuarios` exponía `auth.users`
La vista `public.vista_usuarios` hacía `JOIN` directo contra `auth.users`
(exponiendo el correo real de todos los usuarios) y estaba marcada como
`SECURITY DEFINER`, ignorando RLS. Se confirmó (buscando en todo el
frontend) que **ningún módulo la utilizaba** — el sistema usa
`listar_usuarios()` en su lugar. Se eliminó por completo:
```sql
drop view if exists public.vista_usuarios;
```

### Hallazgo 2 · Funciones ejecutables sin haber iniciado sesión (`anon`)
El Security Advisor detectó que numerosas funciones `SECURITY DEFINER`
eran ejecutables por el rol `anon` (visitante sin sesión) vía
`/rest/v1/rpc/<funcion>`. Al investigar la causa raíz con
`information_schema.routine_privileges`, se confirmó que el problema tenía
**dos orígenes distintos**:
- La mayoría de las funciones tenían el permiso otorgado a **`PUBLIC`**
  (el pseudo-rol "todos"), del cual `anon` hereda automáticamente. Un
  `REVOKE ... FROM anon` simple no bastaba en estos casos.
- Un grupo adicional de ~20 funciones sí tenía un `GRANT` **directo y
  explícito** a `anon`.

Se revocó el acceso en ambas capas (de `PUBLIC` primero, de `anon` directo
después), dejando como única excepción intencional la función
`correo_por_username`, necesaria para resolver el username a un correo
**antes** de que exista sesión (pantalla de login).

Resultado verificado: **ninguna función del esquema `public` es ejecutable
por `anon`**, salvo `correo_por_username`; y **todas** siguen siendo
ejecutables por `authenticated`, confirmando que el frontend no se vio
afectado.

### Hallazgo 3 · `herramientas_especiales` con políticas `USING(true)`
Se encontraron 9 políticas RLS en esta tabla (con duplicados evidentes de
distintas etapas del proyecto: `he_ins`/`herramientas_insert`,
`he_upd`/`herramientas_update`, `he_del`/`herramientas_delete`,
`he_sel`/`herramientas_select`/`v11_herramientas_lectura`), todas para
`INSERT`/`UPDATE`/`DELETE` con condición `true` plana — es decir,
**cualquier usuario autenticado** (incluido el rol `consulta`) podía
crear, editar o borrar herramientas directo en la base, sin importar que
el botón correspondiente estuviera oculto en el frontend para ese rol.

Se eliminaron las 9 políticas y se reemplazaron por 4 políticas limpias:
- `SELECT`: todos los autenticados pueden ver el inventario (sin cambio de fondo).
- `INSERT` / `UPDATE` / `DELETE`: únicamente si el usuario que hace la
  petición tiene, en la tabla `perfiles`, `rol IN ('administrador','recepcion')`
  y `activo = true` (verificado con un `EXISTS` contra `auth.uid()`).

### Hallazgo 4 · Verificación de las tablas centrales del negocio
Se auditaron también `cotizaciones`, `pagos`, `detalle_cotizacion`,
`clientes`, `vehiculos`, `ordenes_trabajo`, `orden_trabajo_detalle` y
`orden_trabajo_piezas`. A diferencia de `herramientas_especiales`, se
confirmó que estas **ya contaban con seguridad real** desde una etapa
anterior del proyecto: las operaciones de escritura usan la función
`es_staff()` (para cotizaciones/pagos/detalle/clientes/vehículos) o
dependen de funciones `SECURITY DEFINER` propias
(`generar_orden_trabajo`, `guardar_avance_orden`, `finalizar_orden`) para
las tablas de órdenes de trabajo, que validan el rol internamente antes de
insertar. Se confirmó también, con el propio Eder, que `cotizaciones`
nunca se elimina (solo se cancela o cierra cambiando su estado), por lo
que la ausencia intencional de una política `DELETE` en esa tabla es
correcta y no requiere corrección.

El único ajuste realizado en este grupo fue de **consistencia** (no de
seguridad): las 3 políticas de `orden_trabajo_piezas` tenían
`roles: {public}` en vez de `{authenticated}` como el resto del sistema;
se recrearon idénticas en su condición pero homologadas a `{authenticated}`.

### Hallazgo 5 · 44 funciones sin `search_path` fijo
El Security Advisor marcó 44 funciones sin `search_path` fijo
(`function_search_path_mutable`), un riesgo bajo pero recomendado de
corregir: sin este ajuste, en teoría alguien con permisos para crear
objetos en la base podría intentar "engañar" a una función para que
resuelva un nombre de tabla/esquema hacia un objeto falso. Se corrigió con
`ALTER FUNCTION ... SET search_path = public` en las 44 funciones, sin
modificar una sola línea de su lógica interna (evitando así el riesgo de
`CREATE OR REPLACE FUNCTION`, que ya había dado el error `42P13` en V11 al
intentar cambiar el tipo de retorno de una función).

### Hallazgo 6 · Bucket de Storage `evidencias` con lectura pública
La política `lectura_publica_evidencias` sobre `storage.objects` permitía
`SELECT` (ver y **listar**) todo el contenido del bucket `evidencias` para
el rol `public`, es decir, sin necesidad de sesión iniciada. Se confirmó
con Eder que las evidencias fotográficas de las cotizaciones **siempre**
se consultan con sesión iniciada dentro del sistema, y que los clientes
externos del taller no tienen ni deben tener acceso a estos archivos. Se
recreó la misma política restringida a `roles: {authenticated}`.

### Hallazgo 7 · Protección de contraseñas
Se revisó la política de contraseñas del proveedor Email en Supabase Auth:
- **Longitud mínima:** se subió de 6 a 8 caracteres.
- **Requisitos de complejidad:** se activó la exigencia de combinar tipos
  de caracteres (antes no había ninguna regla más allá de la longitud).
- **Leaked Password Protection** (verificación contra contraseñas
  filtradas vía HaveIBeenPwned): **no se pudo activar**; Supabase la
  reserva para proyectos en plan **Pro o superior**, y el proyecto opera
  actualmente en plan **Free**. Queda documentado en el Backlog para
  activarse si el proyecto migra de plan en el futuro.

### 📌 Aclaración importante sobre avisos que se dejaron TAL CUAL (a propósito)
El Security Advisor, después de las correcciones, sigue mostrando dos tipos
de aviso informativo que **no representan un problema** y no deben
"corregirse":
- `anon_security_definer_function_executable` sobre `correo_por_username`:
  es intencional, se requiere para el login antes de tener sesión.
- `authenticated_security_definer_function_executable` sobre ~30 funciones
  normales de la aplicación (`buscar_clientes`, `generar_orden_trabajo`,
  `prestar_herramienta`, etc.): es el comportamiento esperado, ya que estas
  funciones **deben** poder ser llamadas por cualquier usuario con sesión
  iniciada para que el sistema opere con normalidad. Revocar este acceso
  rompería la aplicación por completo.

## ⚙️ Guía de instalación desde cero (referencia rápida)

1. Crear proyecto en Supabase.
2. SQL Editor → Run en orden: `schema.sql` → `actualizacion_permisos_archivos.sql`
   → `actualizacion_usuarios.sql` → `01_funciones_admin.sql` → `V5_01_base_datos.sql`
   → `V6_01_base_datos_completo.sql` → (scripts de Catálogo Maestro / Órdenes de
   Trabajo / Herramienta Especial vigentes) → `orden_trabajo_piezas.sql` (V11.2)
   → scripts de seguridad de V11.4 (ver carpeta `supabase/seguridad/`).
3. Desplegar Edge Functions `crear-usuario` y `gestion-usuario`
   (apagar "Verify JWT with legacy secret" en ambas).
4. Crear primer admin: `update public.perfiles set rol='administrador', activo=true where id='UUID';`
5. Importar `catalogo_autos.csv` a la tabla `catalogo_autos`.
6. Configurar `assets/config.js` con las credenciales de tu proyecto Supabase:
   ```js
   const SUPABASE_URL = "https://TU-PROYECTO.supabase.co";
   const SUPABASE_ANON_KEY = "TU_ANON_PUBLIC_KEY";
   ```
   > La `anon key` es pública por diseño (Supabase la protege con las
   > políticas RLS del schema). **Nunca** pongas aquí la `service_role` key;
   > esa solo vive del lado del servidor, dentro de las Edge Functions.
7. Subir a GitHub Pages (raíz del repositorio):
   - `index.html`
   - `assets/app.js`, `assets/v9.js`, `assets/config.js`, `assets/styles.css`, `assets/logo.png`
   - `favicon.ico`, `favicon-16x16.png`, `favicon-32x32.png`,
     `apple-touch-icon.png`, `android-chrome-192x192.png`,
     `android-chrome-512x512.png`, `site.webmanifest`
8. Tras cada actualización de front: **Ctrl+Shift+R** (o modo incógnito) para
   evitar que el navegador cargue una versión vieja de `app.js`/`v9.js`/`styles.css`
   desde caché. Si el problema persiste, agregar/incrementar el parámetro de
   versión en la URL del script, por ejemplo `assets/app.js?v=11.4`.
9. En Supabase → **Authentication → Sign In / Providers → Email**, verificar
   que "Minimum password length" esté en 8 o más y que "Password requirements"
   tenga una opción seleccionada (no "Select an option").
